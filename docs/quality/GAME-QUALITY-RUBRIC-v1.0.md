# 八款遊戲品質評分規格 核准版 v1.0

**狀態：使用者已核准規格；待固定 GitHub commit 與看板政策。不是任何遊戲的合格證明。**  
整理日期：2026-10-29。對象：八款遊戲 1.0 完整交付；早期可玩切片另報進度，不能當完整作品驗收。


## v1.0 核准範圍與修訂優先序

核准記錄：使用者已核准v0.1其餘內容，並指定第9維以桌面端正常使用為準；行動端完整測試因資源限制不列為通過門檻。

**解讀範圍：** 核准的是評分規格；不是核准八款遊戲成績、不是發布／改分享／開新外部來源的授權。第9維與全文連帶平台要求，以本節的桌面必要範圍為準：其他維度、附錄、原歷史文件若要求行動端／跨裝置必測，該部分降為非阻擋；桌面部分、內容數量、玩法、GUI、實聽、GPU／效能、可靠性與獨立評分規則保留。未測必要桌面項仍null。安全或進度損壞若也影響桌面／共用資料仍阻擋，不能用行動端豁免掩蓋。

行動端檢查記 `not_run`、已知限制與已測環境；不是「通過」或品質分數0。原 `mobile-touch` 保留為非阻擋記錄。其他三個必要矩陣全部保留。

## 先看這一頁

依使用者核准，沿用原始製作文件的 **10 個維度，每個維度都要至少 90 分**，不是平均 90 分。每個維度都有「評什麼、如何計分、必須實測什麼」。不靠測試數量灌分，也不以模擬通關代替玩家操作。

1. 每款須有固定版本、原始碼 commit、runtime 檔案指紋及可實際開啟的同版候選。
2. 製作者交件，非製作者獨立評分；兩位品控各保留自己的證據與判斷，不複製分數或平均掉反例。
3. **未測／缺證據＝null（待評）**，不是 0 分，更不是 90 分。已確認失敗可以先報問題，不必等完整評分。
4. 桌面原生畫面、實際輸入、音效實聽、GPU／效能與桌面環境相容性須有相應實測；CPU、mock、打包成功只證明各自有限範圍。
5. 歷史文件的非阻擋新手／重玩研究仍是研究：沒招募到真人只標「未研究」，不新增招募硬門檻、不虛構滿意度。
6. 本文件記錄已核准標準；固定 GitHub commit 與看板政策另依既有授權執行；此規格本身不變更分享權限或作品分數。

## 一、統一計分方法（已核准）

每維有五個子項。每個子項先列出可判定的要求與案例，再計分：

| 子項情況 | 基礎分（每項上限 18） |
|---|---:|
| 必要證據未完成／不能對應同候選 | null；整個維度先不計總分 |
| 全部必達要求通過，無影響該要求的未解問題 | 18 |
| 有 k 個不同、已證實未達的要求 | max(0, 18 − 2k) |
| 核心能力不存在／整個子項無法正常使用 | 0 |

同一根因在同一子項只算一次；若真正影響另一子項，須分別說明影響，不以重複截圖重複扣分。已測失敗不能用「缺資料」隱藏；記錄 fail 與重現步驟，但其他必要部分未測時總分仍為 null。

**維度分數＝五子項基礎分合計＋卓越加分（0–10）。** 每子項另外最多 2 分：
- ＋1：該子項對應的「加分驗證」完整執行，對正常使用有實際價值，提供與基準的可核對差異；僅聲稱更漂亮／更好玩不算。
- 再＋1：另一位非製作者使用同版獨立重現該改善，沒有新反例。
- 五子項全部必達要求通過才開放任何加分。新增測試數量、跑得更久、文件更長本身都不加分。

**硬上限：**任何必達要求失敗，該維度最高 89；核心體驗不可用、重大錯誤／明顯不符玩法約定最高 69。已知 P0／P1 無論分數多少都不能交付。90 表示所有必達項過關；91–94 是有局部額外品質證據；95–100 須多項可重現的額外品質證據；100 不等於永遠無 bug。

例：操作五子項全過＝90；其中兩項有改善證據且獨立重現，各＋2，得94。若其中一項仍有黏鍵，即使其他項優秀也不能以加分補成90。未做真觸控則行動端檢查標 not_run 並列限制，不能把鍵盤測試填到手機欄；此不阻擋桌面評分，也不算手機已通過。

每一扣分須記 `requirementId / defectId / 預期 / 實際 / 重現步驟 / 證據 / 影響子項 / 分數`。主觀品質用明確觀察描述，兩品控有分歧保留雙方原分，具體反例未解前不通過。

## 二、十維評分表

下列每維的五列都是 90 分必達要求。加分驗證是選做，不是新的 90 分門檻。
### 1. 玩法完整 `completeness`

| 子項（各18基礎分） | 90分必達要求 | 選做加分驗證（各最多＋2） |
|---|---|---|
| completeness.1 範圍覆蓋 | 本作附錄的 1.0 地圖、角色、敵人、工具、任務、結局與資產數量都有可到達且實作完整的對應；用 coverage 表逐項對照，不把選單文字當內容。 | 額外可選內容的完整性與主流程一致，且沒有犧牲原範圍 |
| completeness.2 完整循環 | 從新存檔、教學、正常操作到勝敗／章節結束、結算、再玩均可走通；療癒作以日循環及慶典收束，不強加死亡。 | 返回遊戲的上下文提示讓中斷後可直接理解下一步 |
| completeness.3 目標與後果 | 玩家能理解目標、進度、成功失敗原因；獎勵、選擇與結局是真實生效，無假獎勵或假排行榜。 | 不同分支的後果可在回顧中清楚對照 |
| completeness.4 三維核心 | 主角色、可互動物、主要場景為真正三維幾何；碰撞、深度、動畫與鏡頭一致，HUD/粒子可平面。 | 多視角觀察的細節與互動回饋一致，無裝飾誤導 |
| completeness.5 邊界與恢復 | 已承諾入口皆可用，無死按鈕、不可完成路徑、永久卡關；附錄要求的失敗恢復及重玩隔離成立。 | 較少見但合理的流程排列仍可完成且能明確回復 |

**最低證據／測法：** 設計—實作—證據矩陣；至少三段完整流程（成功、失敗／恢復、再玩）；本作所有必測內容覆蓋表；真三維執行證據。不能用瞬移至終點、注入勝利狀態或只呼叫隱藏 handler 證明正常通關。

### 2. 操作手感 `controls`

| 子項（各18基礎分） | 90分必達要求 | 選做加分驗證（各最多＋2） |
|---|---|---|
| controls.1 輸入一致 | 桌面鍵鼠動作可預測、提示一致；按住、放開、取消與失焦均符合規則。觸控／多指盡量兼容，未測列非阻擋限制。 | 可選控制方式提供同等完整操作，不迫使用不舒服手勢 |
| controls.2 即時回饋 | 移動、瞄準、選格、跳躍／操控和互動有可見回應；測量區分設計前搖和輸入延遲。 | 在同測量方法下減少可感延遲且不損動畫辨識 |
| controls.3 判定公平 | 可見命中／碰撞／落點與真實判定一致；附錄時間窗、幀率重播及防作弊要求逐項通過。 | 極限邊界仍清楚可預測，失敗回顧能說明原因 |
| controls.4 鏡頭舒適 | 牆角、狹窄處、坡道與前景遮擋不遮住關鍵目標；需要的回正、縮放或減少動態可用。 | 長時間移動的視線變化更穩定且不犧牲前方資訊 |
| controls.5 生命週期 | 暫停、切頁、恢復、重啟不黏鍵、不保留過期攻擊或失效指標；低幀率也可完成核心動作。 | 額外輸入裝置／切換情境有清楚且無破壞的恢復 |

**最低證據／測法：** 正常與低 FPS 至少各記錄核心動作；歷史至少20次操作／時序檢查及每作更嚴必測；原生輸入錄影與事件時間。建議延遲 p95 桌機≤100ms（手機≤150ms僅非阻擋參考），須先固定測法／硬體再核定，不把動畫前搖誤算。

### 3. 樂趣與重玩 `replayability`

| 子項（各18基礎分） | 90分必達要求 | 選做加分驗證（各最多＋2） |
|---|---|---|
| replayability.1 有意義選擇 | 路線、工具、流派／庭園安排帶來可解釋代價與收益，不是假選擇。 | 額外有效策略與既有策略各有合理適用情境 |
| replayability.2 學習回饋 | 結果提供可理解的改進線索，下一局知道能改什麼；不只顯示分數。 | 回顧能指出具體決策與結果的關聯 |
| replayability.3 變化與目標 | 至少三次局／章節／遊戲日記錄中有可描述策略或內容差異，存在合理下一目標。 | 熟練後仍有不靠數值膨脹的新解法 |
| replayability.4 節奏尊重玩家 | 無強迫真實時間等待、離線懲罰、虛構多人或假獎勵；失敗重試成本符合 brief。 | 重玩或練習入口省去已理解的重複步驟 |
| replayability.5 選擇平衡 | 不存在全面碾壓而令其他承諾選項失去意義的設計；各作平衡／路線要求成立。 | 兩位評者可用不同策略達目標並說明取捨 |

**最低證據／測法：** 三次實際流程的決策、勝敗原因、下一次嘗試目標及平衡案例。智能體能提供設計判斷，不假稱真人喜好或留存率；原非阻擋玩家研究另列未研究。

### 4. 美術與可讀性 `visuals`

| 子項（各18基礎分） | 90分必達要求 | 選做加分驗證（各最多＋2） |
|---|---|---|
| visuals.1 三維完成度 | 模型輪廓、材質、光影和場景風格一致；主要內容不是灰盒／佔位或平面冒充。 | 關鍵物件近看、側背面與遠看均保持一致完成度 |
| visuals.2 威脅與互動 | 最小畫面仍能辨認玩家、危險、可互動物與狀態；不只靠紅綠色差。 | 不同背景／亮度下資訊仍清楚且有冗餘提示 |
| visuals.3 動作表達 | 動作、前搖、命中、受損和結果視覺對應規則；有要求的骨架 clips 完整。 | 動作過渡更自然而不模糊判定時間 |
| visuals.4 畫面整潔 | 無明顯破圖、裁切、穿模、透明排序錯誤；特效不蓋住必要資訊。 | 高負荷場景仍有穩定層次與低干擾效果 |
| visuals.5 鏡頭與介面 | 遮擋與恢復正確，文字／HUD在目標尺寸可讀，減少動態後不損資訊。 | 不同鏡頭／介面縮放仍保有內容構圖與讀取效率 |

**最低證據／測法：** 入口、繁忙場景、結算及最小畫面實際截圖／錄影；模型多角度／幾何檢查；遮擋、陰影、透明、色彩替代與減少動態案例。靜態美圖不能代替執行畫面。

### 5. 音效與混音 `audio`

| 子項（各18基礎分） | 90分必達要求 | 選做加分驗證（各最多＋2） |
|---|---|---|
| audio.1 事件覆蓋 | 核心動作、危險、成功、介面均有符合遊戲風格且能辨識的聲音。 | 不同材質／狀態聲音有實際辨識價值 |
| audio.2 混音品質 | 耳機與喇叭實聽無明顯破音、刺耳堆疊、音量突跳或遮蓋重要提示。 | 密集操作時層次更清楚且疲勞感有具體改善記錄 |
| audio.3 控制與保存 | 音樂／音效音量及靜音可調、重載保存；已在播放的聲音也遵守設定。 | 介面能預聽且避免突發高音量，操作回饋一致 |
| audio.4 生命週期 | 使用者手勢後才開始；暫停、失焦、重啟與切局不重疊舊音軌／延遲回呼。 | 快速切換與裝置恢復仍有自然且不漏停的轉場 |
| audio.5 無音與來源 | 重要聲音有視覺／文字替代，無音也能完成主線；音訊來源／授權可追溯。 | 替代提示不顯雜亂且支援細緻環境音控制 |

**最低證據／測法：** 實聽者、桌面耳機及喇叭設備、具體時段／事件清單；20次快速操作、音量切換、靜音重載、暫停切局測試。AudioContext mock／節點數正確不等實際聽過。無實聽能力時此維度維持null。

### 6. 教學與可及性 `onboarding`

| 子項（各18基礎分） | 90分必達要求 | 選做加分驗證（各最多＋2） |
|---|---|---|
| onboarding.1 獨立上手 | 未讀實作的評者從新存檔只靠遊戲內提示完成教學與第一個完整核心循環。 | 再次回來仍可由遊戲內資訊理解操作與目標 |
| onboarding.2 目標與說明 | 目標、按鍵、資源、失敗原因及下一步清楚；說明可重開，不靠作者口頭提示。 | 說明依當前情境給出具體提示而不劇透整個解法 |
| onboarding.3 介面操作 | 桌面選單鍵盤／焦點與滑鼠點選可用，必要文字可讀且不遮關鍵操作；觸控目標盡量兼容，未測列限制。 | 額外輸入需求下仍可完成相同選單流程 |
| onboarding.4 感官設定 | 靜音、減少動態／閃光及非單一色彩提示可用；敘事文字和速度選項符合brief。 | 設定變更即時、可逆且在完整流程一致生效 |
| onboarding.5 限制誠實 | 已發現嚴重使用障礙修正；未覆蓋輔助科技／輸入方式明列，不宣稱全面無障礙。 | 已知限制有有效替代途徑並經獨立驗證 |

**最低證據／測法：** 全新存檔首次上手錄影／操作紀錄與完成時間；無作者介入的獨立評者紀錄；桌面鍵盤焦點、滑鼠、文字與設定測試；觸控檢查非阻擋。招募5人比例研究不是90分門檻。

### 7. 效能 `performance`

| 子項（各18基礎分） | 90分必達要求 | 選做加分驗證（各最多＋2） |
|---|---|---|
| performance.1 測量基準 | 先固定實際最低硬體、OS/瀏覽器、畫質、解析度/DPR、繁忙場景、冷啟動網路及版本；失敗後不能暗改基準。 | 額外可用畫質檔有清楚品質／效能取捨且不誤導 |
| performance.2 幀時間 | 指定實機繁忙場景至少120秒通過核定p95門檻並提供原始樣本，不只報平均FPS。 | 同基準可見卡頓進一步減少且畫質不退步 |
| performance.3 長時穩定 | 至少15分鐘實際遊玩及10次重啟，不出現持續資源增長、累積聲音／計時器或可見性能劣化。 | 長流程場景切換成本更穩定且可重現 |
| performance.4 啟動與載入 | 冷啟動達核定可互動時間；資源錯誤可理解且可恢復，不長時間白畫面。 | 載入狀態更有用且在相同條件縮短等待 |
| performance.5 三維預算 | draw calls、三角形、貼圖記憶體、燈光／陰影及DPR有量測；必要時LOD/instancing/品質降級且仍可玩可讀。 | 降低負荷而維持已核定可讀性與主要視覺品質 |

**最低證據／測法：** 真GPU/瀏覽器追蹤、原始frame-time資料與p95計算、設備型號、場景操作、資源趨勢及冷啟動紀錄。歷史建議：桌機1080p p95≤20ms、手機實際解析度p95≤33.3ms（非阻擋參考）；10Mbps/80ms冷啟動可互動≤8秒。這些為待核定基準，沒有指定硬體前不硬判達標；個別brief更長場景仍照做。

### 8. 可靠性與存檔 `reliability`

| 子項（各18基礎分） | 90分必達要求 | 選做加分驗證（各最多＋2） |
|---|---|---|

| reliability.2 交易一致 | 獎勵、購買、任務交付及結算原子且冪等，不因連點／重載複製或扣兩次。 | 中途打斷交易能明確回報並維持一致狀態 |

## 三、版本、角色與交付硬門檻

- 固定 `rubricId + rubricVersion + GitHub commit`；使用者已核准內容；正式政策須綁定本文件所在的真實遠端commit，不能假填或以浮動分支代替。
- 同一候選用 `gameId / candidateId / source commit / runtime manifest SHA256 / 可訪候選URL / submittedAt / 真makerSourceTaskId` 串接。URL可開不代表內容就是該候選；核對實際served bytes或可驗部署指紋。
- maker提供自測，不評自己；品控只評未參與製作且能實測的候選。非作者maker的技術核實仍不是產品品質評分。
- 十維各≥90；必要矩陣 `desktop-keyboard`、`lifecycle`、`save-recovery` 全pass，所有桌面適用的本作必測過關，未解P0/P1=0。`mobile-touch` 為非阻擋檢查，未測標not_run並列限制；必要矩陣綠不豁免其他桌面必測。
- P0：安全／隱私、不可逆資料損失、整體無法啟動。P1：可重現崩潰、卡關、核心操作失敗、已核定桌面支援環境不可玩、常見進度損失。P2/P3依影響記錄；影響90條件的P2照樣不通過，不靠降嚴重度過門檻。
- iframe/宿主入口、開始、暫停、繼續、重啟、離開與清理，及直接遊玩入口皆須驗證；原創／授權來源、建置與必要測試也不可省略。
- 變更runtime後，舊分數不自動移植。列受影響範圍重新測；未受影響證據須明確標沿用理由並綁新指紋，不能把整款舊PASS當新款PASS。
- 使用者親自驗收與獨立品控分開，不能代替使用者聲稱滿意。
